# 改完以后怎么检查

## 完成前必须进行对抗性审核

先尝试推翻“已经完成”的结论，再决定是否放行。逐项对照用户原始目标，检查正常尺寸实图、
连续播放和相邻连接，并记录阻挡问题、证据、未检查项及修复后结果。
自动测试只能证明其实际覆盖的性质，不能替代外观判断。对测试未覆盖的明显问题，不能以已有绿项放行。
静态截图不证明运动速度；顶点身份连续不等于最终像素的运动可读；非空覆盖不等于自然沙流。

3.7 的外观通过结论已在用户反馈后的[对抗性复审](../records/v3.7/adversarial-review.html)中撤回。
保留原工程数据和发布记录，不改旧基线。3.7的历史脚本通过只能说明已有工程证据满足旧检查，
不能作为新的整体视觉放行结论。

## 常用命令

以下命令供 CI 的项目根目录使用，本机不运行测试：

```powershell
# 先看这次改动会连带检查什么，不运行测试
python src/tools/run_regression.py --plan

# 开发中：基础检查 + 关联检查；包含已提交改动时指定原始提交
python src/tools/run_regression.py --base <改动前提交>

# 发布前：完整检查，即使有失败也继续执行其余项目，保留结果
python src/tools/run_regression.py --profile full
```

输出在 `_temp/regression-runs/<本次编号>/`，每项有单独日志和汇总 `report.json`。
`--profile core` 只验证目录、版本、静态检查及检查入口自身，绝不等于整个应用没问题。

## 什么情况不让发布

- 返回码非零、超时、异常、缺少完成标记、检查数量不足、跳过检查，均不算通过。
- 完整回归的任一项失败都阻挡；不自动把历史失败登记成豁免。
- 参考指纹变化需解释并让用户审阅，不能通过 `--save` 把红项变绿。
- 发布检查绑定本次代码、资源、规则、脚本的内容摘要；测试后又修改文件，报告失效。
- 日志被删/改、只跑部分检查、缺少人工检查记录，均不能用于推送。
- 本地 push 钩子检查有效的完整报告，CI 另行重跑自动检查，不只看本地结果。

## 脚本还不能代替的检查

完整自动检查会生成 `review-template.json`，默认每项都是 `pending`。
实际检查后填写检查人、结果和证据文件相对项目路径及 SHA256；记录必须绑定当前摘要。
再次执行时用 `--review <记录文件>`。不能只填“已通过”而没有证据。

| 项目 | 需要实际确认的内容 |
|---|---|
| `visual` | 同尺寸、同种子、同时间的前后对照；开局/中段/末段，全部配色与颗粒档位，竖屏/横屏/平板；只允许预先说明的区域变化，尤其看未修改区域 |
| `audio` | MuMu 实际音频输出：开始/暂停/恢复/重置，全部音效、完成播报只一次；脚本桩测试不是“耳朵听过” |
| `performance` | 同一 MuMu/环境/参数的前后重复测量；比较 1% low、最慢帧，不减少沙粒或可见细节 |

证据文件存在且摘要相符，只能防止缺项或用旧结果；内容是否可信仍需检查人负责。
这些记录不是自动化覆盖。`--automation-only` 供 CI 重跑自动项目，不生成可发布结论；
